## 2. OWASP MASVS, L2 testing profile (mobile)

MASVS v2 defines control groups; the levels L1, L2 and R are testing profiles in the OWASP MAS testing guide. Harbour targets L2 for all groups and adds selected resilience controls because the master prompt requires root and jailbreak detection.

| Control group | How Harbour meets it | Phase |
| --- | --- | --- |
| MASVS-STORAGE | Local database encrypted with SQLCipher (AES-256). The key is kept in expo-secure-store with `WHEN_PASSCODE_SET_THIS_DEVICE_ONLY`; on devices with strong biometrics it also needs `requireAuthentication`, so reading it shows Face ID or a fingerprint. On passcode-only devices expo-secure-store cannot require the passcode for the key: it is readable by the app whenever the device is unlocked, and the passcode prompt before the database opens is a check in the app, not a lock on the key (security review S9; decision H-125). Database excluded from device backups; no personal data in logs; screen capture on record screens: Android `FLAG_SECURE` blocks screenshots and recording and blanks the app-switcher preview; on iOS expo-screen-capture hides the app's window from screenshots and screen recordings, which capture a blank screen (it relies on the secure text field layer rather than a documented iOS API, so it is checked on a device before each release), and the app-switcher snapshot is blurred while signed in; identifiers not selectable. When a session ends with entries unsent, only those entries stay on the device, encrypted, until their owner sends them or the owner or a manager deletes them; nothing is deleted automatically and the hold escalates to a manager at `mobile.held_entries_max_days`. Deleting them needs the owner's or a manager's sign-in on the device, not only the passcode. Each deletion is put on record on the device before anything is deleted, as a keystore tombstone holding a coded reason, its stage and opaque ids, and sent to the API (`POST /v1/sync/discards`) one stage at a time: requested, then deleted or failed. A member of staff's own entries may be deleted while the request waits to be sent; anyone else's, or entries whose owner is unknown, only once the API has acknowledged it, and the API asks for `safety.incident.manage` for those. No free text is sent or kept in the keystore: the API records the coded reason, and words given when removing one refused entry stay in the encrypted database until the server has the deletion, then go. A deletion always lists its entry ids unless nothing on the device could ever be read; a cancelled biometric prompt refuses it. After a hold the ended session is signed out on the server once the hold's report has gone, or after an hour (security review round 5, S-L3 and S-L4). A tombstone is never dropped before the API has it (security reviews round 3, M1 to M3, and round 4, M1 to M3; care.md section 6). It names the device the entries were held on, so a stage sent from the device's next database still closes that device's task; the API takes at most 20 new deletion records a day from each person, with or without ids (round 6). A 401, or a 403 with one of the API's session codes, ends the session; any other 403 the API sends on the sync token withdraws the access Care mode needs and holds or wipes the same way; a 403 with no problem body, an HTML page or the web application firewall's `edge_blocked` is checked against `GET /v1/me` in the session's organisation first, and ends the session only when that answers 401, a session code, or without `people.person.read` (round 3 and round 4, H1) | Phase 0 (SQLCipher store); remaining Phase 1 |
| MASVS-CRYPTO | Platform keystores only (iOS Keychain and Secure Enclave, Android Keystore); no hard-coded keys | Phase 0 |
| MASVS-AUTH | Server-side authentication; biometric unlock bound to a keystore key (`BIOMETRIC_STRONG`) with PIN fallback; auto-lock after 2 minutes on personal devices and 30 seconds by default on shared devices; step-up for sensitive actions. Shared devices: [kiosk.md](kiosk.md) | Phase 0 (biometric lock); kiosk Phase 1 |
| MASVS-NETWORK | TLS only; platform certificate validation; identity pinning for endpoints Thapsus controls (L2) | Pinning approach needs an ADR (rotation and recovery) `[ADR - engineering]`; Phase 1 |
| MASVS-PLATFORM | Deep links validated (tenant and person IDs re-checked, hazard HZ-001); no WebViews for record content; permissions requested at first use with an explanation; foreground-only location | Phase 1 |
| MASVS-CODE | Minimum OS versions enforced; app refuses writes and prompts update when more than one schema version behind; dependency scanning; EAS Update only for JavaScript and assets | Phase 1 |
| MASVS-RESILIENCE (beyond L2) | Root and jailbreak detection warns and blocks eMAR | Phase 2 (with eMAR) |
| MASVS-PRIVACY | Data minimisation (assigned people and next 7 days only); no third-party tracking or advertising SDKs; Apple privacy manifest and labels; Google Play Data safety form; in-app account deletion request flow | Phase 1 |

## 3. NCSC guidance

| Topic | NCSC guidance | Harbour |
| --- | --- | --- |
| MFA | Prefer phishing-resistant FIDO2 or passkeys, then authenticator apps; SMS is weaker | Passkeys and TOTP; SMS only as a documented exception per user, recorded with reason; MFA mandatory for all roles that can read care records |
| Passwords | Length over complexity; deny common and breached passwords; no forced expiry; allow paste and password managers; throttle rather than lock out | Minimum 12 characters; deny list; no expiry; paste allowed; throttling with increasing delay per account and per IP |
| Logging | Decide what to log, protect integrity, synchronise time, centralise, retain long enough to investigate | Security logs at least 6 months, UTC timestamps from synchronised clocks, tamper-evident (append-only table, pgAudit, a security log bucket in Cloud Logging, europe-west2, kept 400 days or more and locked in prod), scrubbed of personal data |
